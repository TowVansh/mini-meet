Abstract

Mini-Meet is a 2–4 person audio/video calling application implemented from the socket level up in C. A TCP signalling server written by us introduces the participants. Each client discovers its public address with STUN and traverses NAT with UDP hole punching. VP8 video and Opus audio then flow directly between peers in our own RTP-style framing layer over UDP, encrypted end to end with X25519 key agreement and ChaCha20-Poly1305. The receiver uses an adaptive, timestamp-driven jitter buffer, and repairs or conceals losses with NACK retransmission, keyframe requests and Opus FEC/PLC. RTCP receiver reports drive an AIMD rate controller with slow start, a delay-based congestion signal and feedback-starvation detection.

We evaluated the system in 28 runs over Linux network namespaces with per-direction tc netem impairment, plus a jitter-buffer on/off experiment, a single call through changing bandwidth, a 4-person mesh test and a real call between two different networks. Random loss up to 5 % is invisible to the user. Without rate control, a 1 Mbit/s bottleneck drives RTT above 10 s (bufferbloat). With it the call stays at 20 fps with a 3 ms RTT. The jitter buffer reduces audio concealment under ±30 ms jitter from 88 % to 0.1 %, at the cost of about 140 ms of added delay. The real cross-network call connected peer-to-peer through both NATs (srflx→srflx).

1. Introduction and Objectives

Video calls combine two very different kinds of traffic. Call setup needs a few hundred bytes that must arrive reliably and in order. Media needs a continuous stream of time-critical packets, where a late packet is as useless as a lost one. The project builds both halves ourselves and measures how a real-time stream behaves when the network loses, delays, reorders or throttles packets.

2. System Architecture

The system consists of three programs: mm-server (signalling), mm-stun (an optional STUN server) and mm (the call client). All networking is our own code on plain sockets. Libraries are used only for capture and decoding of camera and file input (FFmpeg), the codecs (libvpx, libopus), the window and speakers (SDL2), and the cryptographic primitives (libsodium).

3. Signalling Protocol

TCP is a byte stream, so a single recv() may return half a message or several. Every message is therefore one ASCII line ending in \n, at most 512 bytes, made of space-separated tokens. The receiver buffers bytes until a newline completes a line. Because the protocol is plain text, it can be driven by hand with telnet.

Validation. The server rejects lines over 512 bytes (and closes the connection), names outside [A-Za-z0-9_-]{1,32}, malformed candidates and keys, and relaying to a peer outside the sender's room. It runs as a single thread with one select() loop (no locks), with FD_SETSIZE raised on Windows.

Liveness. The server drops a connection that has been silent for 20 s, and its peers receive PEER_LEFT. Testing showed that under heavy bufferbloat a client's PINGs can be stuck in the same queue as its media, so the server times it out while the call is still working. A client therefore keeps a peer for as long as that peer's media keeps arriving (it is removed 3 s after its packets stop), and it removes any peer silent for 30 s on its own, without the server.

4. Media Framing Layer

STUN, RTP and RTCP share one UDP socket and are demultiplexed by their first byte (RFC 7983). STUN starts with 0–3 and carries the magic cookie 0x2112A442. RTP and RTCP start with 128–191, and RTCP is recognised by packet type 200–206 in the second byte (RFC 5761). The source address then identifies the peer, and the payload type identifies the stream.

5. NAT Traversal

A NAT rewrites the source address of outgoing packets and admits incoming packets only if they match a mapping it created. Two peers behind NAT therefore cannot simply send to each other. Mini-Meet uses a simplified ICE (RFC 8445):

  1. Gather: the host candidate is the LAN address. The server-reflexive (srflx) candidate is the public IP:port that a STUN Binding request reports in XOR-MAPPED-ADDRESS. The address is XORed with the magic cookie so that NAT helpers do not rewrite it.
  2. Exchange: candidates are sent as CAND lines through the signalling server.
  3. Check (hole punching): both peers send STUN Binding requests to every candidate of the other every 100 ms, with USERNAME = "<their-id>:<my-id>". Each outgoing packet opens a mapping in the sender's own NAT, so the other side's packets can come back in. A request from an unknown address becomes a peer-reflexive candidate.
  4. Select and keep alive: the first candidate that answers carries the media. A Binding request every 2.5 s keeps the NAT mappings from expiring.

Hole punching fails when both sides (or one symmetric side and one port-restricted side) are behind a symmetric NAT, which assigns a new public port per destination. The client detects this after 15 s and reports that a TURN relay would be needed.

6. Jitter Buffer and Loss Repair

6.1 Playout clock (jitter buffer)

Packets leave at even intervals (20 ms audio frames, 50 ms video frames) but arrive unevenly. Playing them on arrival gives choppy output. For every arriving packet the receiver records

offset = arrival time − media time (the RTP timestamp in µs),   and plays media time T at   T + P95(last 64 offsets).

About 95 % of packets are therefore already present when their turn comes, and playout follows the sender's pace rather than the network's. The delay adapts by itself: a few milliseconds on a clean link, about 140 ms under ±30 ms jitter and about 220 ms under ±60 ms. Using the 95th percentile instead of the maximum trades ~5 % late packets (which concealment hides) for much lower latency. A video frame is decoded only when it is complete and due. Audio adds a 25 ms margin so that the next packet, which carries the FEC copy, is usually present. A late packet is dropped but still updates the clock, which is how the buffer learns to grow.

6.2 Loss repair and concealment

MechanismHow it works
Gap → NACKA sequence gap puts the missing numbers on a list. After a reordering wait of about 2 × jitter (5–80 ms) they are requested with RTCP Generic NACK (packet ID + 16-bit bitmask, up to 17 losses per entry), resent every 1.5 × RTT, at most 4 tries.
RetransmissionThe sender keeps the last 1024 video packets and resends them as PT 97: selective-repeat ARQ with a deadline.
Skip + PLIA frame not repaired within max(120 ms, 1.5 × RTT + 40 ms) is skipped. Later frames reference it, so the receiver waits for a keyframe and requests one with PLI (rate-limited to at least 1.5 × RTT apart). The visible effect is a freeze.
Opus FEC / PLCA missing audio frame is rebuilt from the in-band FEC copy in the next packet if that has arrived, otherwise packet loss concealment extrapolates it. The encoder is told the measured loss rate so it can size the FEC.
MetricsPer second: playout_sd_ms (standard deviation of shown-frame intervals), jb_delay_ms, freezes (a gap longer than max(3 × average, average + 150 ms)), audio concealment %.

7. Feedback and Rate Control

7.1 Receiver feedback (RTCP, RFC 3550)

  • Loss: expected = extended highest sequence − base + 1; lost = expected − received; fraction lost = (lostinterval × 256) / expectedinterval.
  • Interarrival jitter: D = (Rj − Ri) − (Sj − Si); J ← J + (|D| − J)/16, in timestamp units.
  • Round-trip time: RTT = A − LSR − DLSR, where A is the time a report arrives, LSR is our Sender Report time that it echoes, and DLSR is how long the peer held it. Both A and LSR come from our own clock, so no clock synchronisation is needed. Example: SR sent at 10.000 s, held 0.050 s, report arrives at 10.130 s, so RTT = 80 ms.

7.2 AIMD controller

Level0123 (start)45
Video bitrate1200 kbps800500300180100
Resolution640×480640×480480×360320×240320×240160×120
  • Congestion (loss > 8 % or queuing delay > 120 ms): drop two levels (multiplicative decrease). Clean (loss < 2 % and queuing delay < 40 ms) three reports in a row: climb one level (additive increase), giving the TCP-Reno sawtooth.
  • Queuing delay = smoothed RTT − minimum smoothed RTT of the last 10 s, capped at 250 ms above the best RTT ever seen. This is the delay-based idea of TCP Vegas, BBR and WebRTC GCC: back off when a queue starts to fill, before packets are dropped. The window lets a longer path become the new baseline, and the cap stops a standing queue from becoming "normal".
  • Slow start: begin at 300 kbps and climb one level per clean report until the first congestion signal.
  • Feedback starvation: reports normally arrive every second. If none arrive for 2.5 s they are probably stuck in the same queue as the media, so the silence itself is treated as congestion.
  • Bitrate changes are applied live (vpx_codec_enc_config_set). A resolution change restarts the encoder with a keyframe. In a mesh the encoder serves the worst receiver.

8. Security

  • End-to-end media encryption. Each client creates a fresh X25519 key pair and sends its public key through signalling. crypto_kx derives the same two 256-bit session keys (one per direction) on both peers. The server only ever sees public keys, so it cannot decrypt media. Every RTP payload is sealed with ChaCha20-Poly1305 (AEAD). The 12-byte header stays readable, because demultiplexing and sequence numbers need it, but it is authenticated. The nonce is SSRC ‖ seq ‖ PT ‖ timestamp, which is unique per packet. RTCP is encrypted the same way with an index. A tampered packet fails the tag check and is dropped.
  • Man-in-the-middle. A malicious server could substitute keys, so both screens show a short safety code (a hash of both public keys) for the users to compare. Key pairs are never stored, which gives forward secrecy across calls.
  • Server hardening. Line-length limit (DoS), name and candidate validation, relaying only within a room, 4-person cap, idle timeout. STUN checks carry peer IDs in USERNAME.
  • Not covered. No TLS on the signalling channel (keys are protected by the safety code instead), no replay window on media, and no message integrity on STUN checks.

10. Evaluation

10.1 Method

Two Linux network namespaces (mmA 10.10.0.1, mmB 10.10.0.2) are joined by a veth pair and behave like two separate hosts. tc netem runs on both veth ends, so each direction is impaired separately, like a real access link. Clients send a built-in test pattern (VP8, up to 640×480, 20 fps) and a tone (Opus), so every run has identical input. Each run is 10 s clean, then the profile applied mid-call, then 45 s recorded, for 14 profiles × adaptation off (fixed 1200 kbps) / on. Values are steady-state medians (means for loss and concealment). Freezes are summed over both receivers.

Without a buffer most audio frames arrive after their 20 ms slot and must be concealed, and video frames are shown as unevenly as they arrive. It pays for this with 140–220 ms of added delay, the fundamental smoothness-versus-latency trade-off of a jitter buffer.

10.5 Bitrate adaptation across changing network conditions

10.6 Further results

  • 4-person mesh (Windows, release build): all 12 directed streams received at 640×480, 20 fps, ~1190–1220 kbps each, playout spread ~2 ms. Each client uploads three copies (~3.6 Mbit/s).
  • Real cross-network call: srflx→srflx, median RTT 85 ms, loss < 0.6 %. The mobile hotspot's uplink buffered in bursts (RTT spikes to 1.15 s), and the controller followed them down and back up.
  • Recorded media (--file, H.264 + AAC, looped): streamed in real time on Linux and Windows; the viewer received 640×480 at 20 fps with 0 % concealment.

11. Discussion

  • Random loss up to 5 % is invisible. NACK retransmission repairs video before the frame deadline, and Opus FEC keeps audio concealment ≤ 0.4 %. At 10–20 % loss a packet and its retransmission are sometimes both lost. The frame is skipped and a keyframe is awaited, which shows as freezes (23 at 20 %). Rate control reduces this to 15, because smaller frames have fewer packets that can be lost.
  • Constant delay is harmless. At 200 ms RTT the quality equals baseline. The windowed baseline keeps the controller from treating a longer path as congestion; a first version without it stayed at the lowest level permanently, and this test caught the bug.
  • Bandwidth limits need rate control. A fixed 1200 kbps stream into a 1 Mbit/s link fills netem's 1000-packet FIFO (bufferbloat): RTT 10.5 s, 14 % loss, 34 % audio concealed. At 500 kbit/s the video stops. The adaptive sender keeps RTT at 3–10 ms with 0 % loss at 20 fps. In the combined profile the fixed-rate call stalls entirely, while the adaptive call keeps 20 fps at 199 ms RTT.
  • Known weaknesses, all textbook ones:
    • Random (wireless-style) loss and jitter are misread as congestion, so the controller lowers quality unnecessarily (5 % loss → 690 kbps).
    • At 250 kbit/s, feedback-starvation detection backs off within 2.5 s, but the first seconds at full rate have already filled the queue. Even the lowest level plus audio drains it only slowly, so RTT stays high. A "pause video" level, or AQM such as CoDel in the network, would fix it.
    • A larger jitter buffer means more latency.
  • Comparison with a WebRTC prototype built first (browser + Node.js): Chrome's GCC handled the same 1 Mbit/s cap by settling around 50 kbps. Both systems were stuck behind netem's buffer at 250 kbit/s. Our implementation makes every mechanism visible and measurable.

12. Limitations and Future Work

  • No TURN relay: two symmetric NATs cannot connect.
  • Mesh topology limits calls to about 4 people. An SFU with simulcast or SVC would scale, and would let each receiver get the quality its link supports.
  • Signalling over plain TCP: add TLS and STUN message integrity, and a replay window for media.
  • Controller: distinguish random loss from congestion (for example using delay trends), and add a pause-video level for very thin links.
  • IPv4 only. One 45 s run per profile; repeated runs would give confidence intervals.

13. Conclusion

Mini-Meet delivers working 2–4 person audio/video calls written in C on raw sockets, covering signalling, NAT traversal, framing, jitter buffering, loss repair, rate control and encryption. It runs on Windows and Linux and has been verified across two different real networks. The evaluation shows both halves of the real-time loop at work. The receiver-side jitter buffer turns uneven arrivals back into smooth playout (88 % → 0.1 % concealed audio under ±30 ms jitter). The sender-side rate controller, driven by receiver feedback, keeps a call usable on bandwidth-limited links where a fixed-rate stream collapses into seconds of delay. The remaining limitations are well-understood trade-offs of the design.
